## 2026-10-14 [gen_cost][cost] A transcript message with no stop_reason holds only the stream-start output count
Claude Code writes a streamed message once per content block as each block finishes, and every one of those records carries the usage of the stream's start (a handful of output tokens). The final output count comes afterwards with `stop_reason`, and only lands on disk when the message's closing record is written. In background subagents most messages never get one: on PCB-0017-A, 384 of 444 Fable messages, 71 of 644 Opus and 242 of 347 Sonnet had `stop_reason: null`. One session's subagent transcript showed 642 output tokens where cost-state billed 99,849, while input, cache-read and cache-write matched to the token. Across the board's 14 sessions the whole gap was output (Fable 828,900, Opus 78,861, Sonnet 233,667 tokens), so gen_cost left $46.10 of $126.02 "not in the transcript". The final count is nowhere else on disk: the task-notification's `subagent_tokens` is a context size, not output. Cost-state's `modelUsage` has the exact per-model total, so gen_cost now adds each model's missing output to its messages that lack a closing record, shared by visible content size plus half the mean (thinking is stored redacted, so it can't be measured), and reports it as `apportioned_usd`. The per-message share is an estimate (about 35-85% L1 error per message against closed messages), but the per-model total is exact. Unattributed on PCB-0017-A fell to $0.74, which is Haiku side calls that have no transcript message at all. Never trust a transcript's `output_tokens` on a record whose `stop_reason` is null.
